# Run Agent Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** After every load run, the console analyses it with a bounded agent and stores a validated report. The report shows in the inspector's Job view and on the AI Agent page.

**Architecture:** A new package `dev.marwan.console.agent` inside the console, with no new Deployment.
- A scheduled reconciler finds finished load Jobs that have no report.
- It gathers baseline facts from k6's summary line, Prometheus, Kubernetes events, booking-service logs and the oversold invariant.
- It lets the model call up to 5 read-only tools through a JSON protocol.
- It validates the report: every cited fact exists and every number appears in a cited fact. It allows one retry, then falls back to a deterministic report.
- It stores the result in a single ConfigMap.

**Tech Stack:** Java 25, Spring Boot 4.1 (`@Scheduled`), the JDK `HttpClient` against the OpenAI-compatible vLLM endpoint, fabric8 6.13.4, Jackson 3, Angular 20.

**Spec:** `docs/superpowers/specs/2026-09-25-cluster-inspector-and-run-agent-design.md` §8, with §2, §3, §10 and §11. The page it feeds: `docs/superpowers/specs/2026-09-25-site-presentation-design.md` §6.

## Global Constraints

- **Model:** `isvc-qwen3-8b-fp8` at `https://isvc-qwen3-8b-fp8-predictor.sandbox-shared-models.svc.cluster.local:8443/v1`. The name and base URL are config. Thinking is off, temperature 0.2, 60 s per call, 3 min per run.
- **Tool budget:** at most 5 tool calls per run. Tool output is bounded: 40 log lines, 30 points per series, 20 events.
- **Log masking:** logs pass through `LogLines.mask` before they reach the model or storage.
- **A run always gets a report:** when the model fails validation twice, times out or is unreachable, a deterministic report is built from the facts and labelled "model unavailable".
- **No framework:** no LangChain and no new service.

## Rulings made while planning

- **Storage is one ConfigMap `run-analyses`, keeping the newest 12 runs, not one ConfigMap per run as §8.5 says.** The console Role has only get, create and update on configmaps (no list or delete), and CD never applies RBAC. A single object needs no RBAC change and prunes itself. Cost if wrong: the 1 MiB limit. Each run is bounded to 60 KB, so 12 runs is at most 720 KB.
- **JSON protocol, not native tool calling (§8.4 allows either).** It works whatever flags the shared vLLM server was started with. Cost: slightly longer prompts.
- **No bearer token to the model.** The console's ServiceAccount token is a credential for our namespace, and the model is a shared service in another namespace. A 401 falls back to the deterministic report and says so.
- **Pool timeouts are counted per pod, not split by thread.** The JSON log lines are not known to carry the thread name. Cost: the "probe-thread share" of §10's replay cannot be shown.

## Review Focus

1. **A load Job whose pods are already gone** (TTL 900 s, or a console restart). Expected: facts from what remains, with k6 marked unavailable, and still a stored report.
2. **A model that loops, invents a number, times out, or returns non-JSON.** Expected: a stored, valid report every time, with the budget respected.
3. **Two console pods, or a slow analysis overlapping the next tick.** Expected: the same Job is not analysed twice at once. It runs single-flight within the pod, and the ConfigMap is written with its resourceVersion, so a conflict reloads and retries once.
4. **A viewer without the key.** Expected: they can read reports. "Re-analyse" needs the key (it is a POST, so KeyFilter already protects it).
5. **Phone numbers in logs.** Expected: masked in facts, the trail and the prompt.

### Task 1: k6 prints a machine-readable summary; parse it
- In `console/src/main/resources/k6/drop.js`, add a `handleSummary(data)` that returns `{ stdout: 'K6_SUMMARY ' + JSON.stringify({vus, iterations, booked, rejected, notClean, p50, p95, max, durationMs}) + '\n' }`. Add the same to `loadtest/drop.js`.
- New `agent/K6Summary.java`: `static Optional<K6Summary> parse(String log)` finds the last `K6_SUMMARY ` line.
- Test `K6SummaryTest`: the line is found among other lines; a missing line gives empty; malformed JSON gives empty.

### Task 2: Facts and the baseline gatherer
- `agent/Fact.java`: `record Fact(String id, String source, String label, String value)`. `agent/Facts.java`: `add(source, label, value)` numbers the facts F1, F2, … in order.
- `agent/RunWindow.java`: `record RunWindow(String job, String dropId, Instant start, Instant end)`, where end is completion + 30 s.
- `agent/Baseline.java` gathers these, and each source that fails adds a fact saying it was unavailable rather than throwing:
  - k6 from the Job pod's log (`ObjectSource.podLog`);
  - Prometheus peaks through `RangeQuery` (peak pool per pod, 5xx total, peak p95, peak replicas);
  - Warning events for the booking-service and queue-gate Deployments and their pods, within the window;
  - restarts per pod;
  - pool timeouts per booking-service pod (`Connection is not available` in the 500-line tail, within the window);
  - oversold from `DemoStateProvider.currentFor(dropId)`.
- Test `BaselineTest` with `FakeObjectSource`, a lambda `RangeQuery` and a stubbed state. It checks the fact order and ids, that an unavailable source becomes a fact, and that a phone number in a log line is masked.

### Task 3: Tools
- `agent/Tools.java`: `Fact call(String tool, JsonNode args, RunWindow w)` for `pod_logs`, `metric`, `events`, `pod_status` and `endpoints`, each bounded and masked. An unknown tool or bad args returns a fact saying so, never an exception. Pods outside `Scope.ours` are refused.
- Test `ToolsTest`: the bounds (40 lines, 30 points, 20 events), an unknown tool, and a pod out of scope.

### Task 4: Model client
- `agent/ModelClient.java`: `String chat(List<Message> messages, Duration timeout)` POSTs `/chat/completions` with `temperature` 0.2 and `chat_template_kwargs.enable_thinking=false`, and returns `choices[0].message.content`.
  - It trusts the service CA the way `ThanosTenancy` does.
  - It throws `ModelUnavailable` on non-200, timeout or I/O failure.
- Test `ModelClientTest` against a JDK `HttpServer` stub: it checks the request body shape, the content extraction, and non-200 leading to `ModelUnavailable`.

### Task 5: The loop, validation and fallback
- `agent/Validator.java`: `List<String> problems(Report r, Facts f)`. It flags unknown ids, and any number in a claim's text that is missing from its cited facts' values. Numbers are compared as normalised decimal strings.
- `agent/Fallback.java`: `Report from(Facts f)` builds a deterministic report: oversold, clean vs not clean, peak pool per pod, 5xx and restarts, each citing its fact.
- `agent/Analyst.java`: `Analysis analyse(RunWindow w)`:
  1. Baseline.
  2. Up to 5 iterations of: the model returns `{"call":…,"args":…,"why":…}` or `{"done":true}`; the tool runs and its fact is added.
  3. The model is asked for a report.
  4. Validation, one retry with the problems fed back, then the fallback.
  5. A 3-minute deadline overall.
- `agent/Analysis.java` holds job, facts, trail, report, model, `source` (model or fallback), timings and problems.
- Test `AnalystTest` with a scripted `ModelClient`, covering:
  - a clean run;
  - a model that loops (the budget stops at 5);
  - one that invents a number, then corrects it on retry;
  - one that invents twice (fallback);
  - a timeout (fallback);
  - non-JSON (fallback).

### Task 6: Store and reconciler
- `agent/AnalysisStore.java` keeps ConfigMap `run-analyses`, with one key per job (the Analysis JSON) and at most 12 entries, evicting the oldest.
  - It gets, then updates with the resourceVersion. On a 409 it re-reads and retries once. It creates the ConfigMap when missing.
  - It refuses an entry over 60 KB by trimming the trail's results.
- `agent/RunAnalyst.java` is a `@Scheduled(fixedDelay = 10 s)` reconciler.
  - It lists Jobs labelled `app=rembayung-load` that are complete or failed with no entry, and analyses the oldest first, one per tick, on a virtual thread with a single-flight guard.
  - It is off when `console.agent.enabled=false`.
- `@EnableScheduling` goes in `ConsoleConfiguration`.
- Config: `console.agent.enabled`, `base-url`, `model`, with defaults in `application.yml` and env in `deploy/base/console/deployment.yaml`.
- Tests:
  - `AnalysisStoreTest`: eviction at 12, the 409 retry, the size trim. It uses a small `ConfigMapPort` interface, faked in the test.
  - `RunAnalystTest`: skips analysed jobs and running jobs; one per tick.

### Task 7: API
- `GET /api/analyses` returns summaries, newest first.
- `GET /api/analyses/{job}` returns the full analysis, or 404.
- `POST /api/analyses/{job}/rerun` reruns the loop on the stored facts. It needs the key.
- Test `AnalysesControllerTest` (`@WebMvcTest`): the list, a 404, and that the rerun is refused without the key.

### Task 8: UI
- The inspector gains an "Analysis" tab for Jobs that have one. It shows:
  - the three lists with fact chips (a chip click shows the fact);
  - the trail;
  - a footer with the model, whether it is model-written or the fallback, and the duration;
  - Re-analyse for key holders.
- The AI Agent page shows "Latest real report" above the example when `/api/analyses` has one. The badge stays "In progress" until a model-written report exists, then reads "Live".
- Build, then check in the browser at 1680 and 390.

### Task 9: Deploy and verify
- Merge, then run CD.
- Start a rush with the key. Within a minute of the Job finishing, `/api/analyses` lists it, and the inspector and the AI Agent page show it.
- If the model is unreachable, the report is the fallback, and the note says why.
