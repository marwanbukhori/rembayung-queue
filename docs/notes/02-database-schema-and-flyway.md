## Flyway: migrations as version-controlled SQL

Flyway applies numbered SQL files to a database, in order, exactly once each.
It records what it has applied in a table it manages itself
(`flyway_schema_history`), so re-running against an already-migrated database is
a no-op.

```
src/main/resources/db/migration/V1__initial_schema.sql
                   └── default scan location    └── two underscores, not one
```

Both parts of that path are conventions Flyway enforces:

- **`db/migration`** on the classpath is where it looks by default. Nothing
  configures this.
- **`V1__initial_schema.sql`** — `V` for versioned, `1` the version, then a
  **double** underscore, then a free-text description. A single underscore is
  the most common Flyway mistake; the file is silently not picked up.

Spring Boot runs Flyway automatically at startup, before the application is
ready and before Hibernate validates. So by the time any test method executes,
the schema exists.

### Why the schema is hand-written rather than generated

Covered in [note 01](01-project-skeleton-and-spring-boot-basics.md) under
`ddl-auto: validate`, but it is worth restating here because this file is the
proof: **an ORM can generate a schema that stores your objects, but not one
that enforces your invariants.**

Hibernate would have produced `slots` and `bookings` perfectly well. It would
not have produced `ck_slots_seats`, and that constraint is the whole point.

### The Spring Boot 4 trap this task hit

Flyway silently did not run on the first attempt. No error, no warning — the
migration simply never applied and every query failed with
`ORA-00942: table or view does not exist`.

Cause: **Spring Boot 4 split autoconfiguration into per-technology modules.**
`FlywayAutoConfiguration` used to ship inside `spring-boot-autoconfigure`,
which every Boot application gets transitively. In Boot 4 it lives in its own
artifact:

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-flyway</artifactId>
</dependency>
```

`flyway-core` was present the whole time — the *library* was on the classpath,
but the *Spring glue that invokes it* was not.

This is the sharp edge of auto-configuration, and the honest counterweight to
the convenience described in note 01: when auto-configuration is present it
saves you a great deal of wiring, and when it is absent **nothing tells you
so**. The component just never runs. The diagnostic move is to check whether
the `*AutoConfiguration` class is actually on the classpath, not whether the
underlying library is:

```bash
mvn dependency:build-classpath -Dmdep.outputFile=/tmp/cp.txt
for j in $(tr ':' '\n' < /tmp/cp.txt); do
  unzip -l "$j" 2>/dev/null | grep -q FlywayAutoConfiguration && echo "$j"
done
```

`--debug` on a Boot run also prints an auto-configuration report listing what
matched and — more usefully — what did not, and why.

## The schema

```sql
CREATE TABLE slots (
    id           NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    service_date DATE          NOT NULL,
    service_time VARCHAR2(5)   NOT NULL,
    capacity     NUMBER(5)     NOT NULL,
    seats_taken  NUMBER(5)     DEFAULT 0 NOT NULL,
    version      NUMBER(10)    DEFAULT 0 NOT NULL,
    CONSTRAINT uq_slots_datetime UNIQUE (service_date, service_time),
    CONSTRAINT ck_slots_seats CHECK (seats_taken >= 0 AND seats_taken <= capacity)
);
```

### `ck_slots_seats` — the constraint the project exists to demonstrate

```sql
CHECK (seats_taken >= 0 AND seats_taken <= capacity)
```

This is the **last line of defence against overselling**, and it sits below all
application code. If `BookingService` has a race condition, if the expiry
sweeper double-releases a seat, if someone writes a stray `UPDATE` by hand —
Oracle rejects the write.

Two properties make this worth more than an application-level check:

1. **It cannot be bypassed.** Not by a new code path, not by a second service,
   not by a DBA at a SQL prompt.
2. **It is enforced per-statement inside the transaction**, so it holds under
   concurrency without any coordination.

The **lower bound matters as much as the upper one.** `seats_taken >= 0` is not
defensive padding: it is what catches an expiry sweeper releasing seats it
never took. That bug would otherwise silently manufacture capacity — the table
would report fewer seats taken than there are real bookings, and the error
would only surface as customers turning up to a full restaurant.

Task 8 leans on this constraint directly: it hammers a slot with 400 concurrent
bookings and asserts the invariant held. If the application logic were wrong,
this constraint fires and the test fails loudly rather than the system quietly
overselling.

### `uq_slots_datetime`

One row per (date, time) pair. Prevents two rows both claiming to be the 7pm
sitting on the same day, which would split capacity in a way nothing downstream
would notice.

### `version`

Reserved for JPA optimistic locking (`@Version`), added in Task 3. Unused so
far. Note that this project's primary concurrency control is *pessimistic*
(`SELECT ... FOR UPDATE`); the version column is a secondary guard, not the
main mechanism.

```sql
CREATE TABLE bookings (
    id              NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    slot_id         NUMBER        NOT NULL,
    phone           VARCHAR2(20)  NOT NULL,
    party_size      NUMBER(3)     NOT NULL,
    status          VARCHAR2(20)  NOT NULL,
    deposit_cents   NUMBER(10)    NOT NULL,
    idempotency_key VARCHAR2(64)  NOT NULL,
    created_at      TIMESTAMP     DEFAULT SYSTIMESTAMP NOT NULL,
    expires_at      TIMESTAMP     NOT NULL,
    CONSTRAINT fk_bookings_slot FOREIGN KEY (slot_id) REFERENCES slots(id),
    CONSTRAINT uq_bookings_idempotency UNIQUE (idempotency_key),
    CONSTRAINT ck_bookings_party CHECK (party_size > 0),
    CONSTRAINT ck_bookings_status CHECK (status IN
        ('PENDING_DEPOSIT','CONFIRMED','EXPIRED','CANCELLED'))
);
```

### `uq_bookings_idempotency` — where idempotency is actually enforced

A double-tapped submit button, or a client retry after a timeout, must not
produce two bookings.

Task 5 adds an application-level pre-check ("have I seen this key?"), but that
pre-check is **not** the guarantee — two genuinely simultaneous requests both
pass it, because neither has committed when the other looks. The unique
constraint is what makes the loser fail.

The general shape is worth internalising: **an application-level check is an
optimisation; the constraint is the correctness.** The check saves a round trip
in the common case. The constraint is what is true.

`VARCHAR2(64)` accommodates a UUID (36 chars) or a SHA-256 hex digest (64).

### `ck_bookings_status`

Restricts `status` to the four legal values. It duplicates the `BookingStatus`
enum that arrives in Task 3 — deliberately. The enum constrains *this
application*; the constraint constrains *the table*, including anything else
that ever writes to it.

Keeping them in sync is a real maintenance obligation, and the price of the
guarantee.

### `ck_bookings_party`

`party_size > 0`. A zero or negative party would let a booking consume no seats,
or manufacture them.

## Oracle type notes

| Type | Notes |
|---|---|
| `NUMBER(5)` | Up to 5 digits. Covers a 250-seat capacity with room to spare. |
| `NUMBER(10)` | `deposit_cents` — 2000¢ per head across any realistic party. |
| `VARCHAR2(n)` | Oracle's variable-length string. `VARCHAR` exists but Oracle documentation has advised against it for decades. |
| `DATE` | In Oracle this includes a *time* component, unlike the SQL standard. `service_date` stores midnight; `service_time` is a separate `VARCHAR2(5)` holding `'19:00'`. |
| `TIMESTAMP` | Sub-second precision. Used for `created_at` / `expires_at`. |
| `SYSTIMESTAMP` | Database server clock, used as the `created_at` default. |
| `GENERATED BY DEFAULT AS IDENTITY` | Auto-increment. *By default* (rather than `ALWAYS`) permits an explicit id on insert, which JPA needs. |

### One thing Oracle does not do

**Oracle does not automatically index foreign key columns.** Primary keys and
unique constraints get an index for free; foreign keys do not.

So `bookings.slot_id` is currently unindexed. That is fine for this phase —
nothing queries bookings by slot; the sweeper reaches slots by primary key —
but a "show me every booking for this slot" query would full-scan. Noted as a
deferred item rather than added speculatively.

### `ix_bookings_sweep`

```sql
CREATE INDEX ix_bookings_sweep ON bookings (status, expires_at);
```

The one index that *is* here, because Task 7's expiry sweeper queries exactly
`WHERE status = ? AND expires_at < ?`. Column order matches the query:
equality predicate first, range predicate second, which is the ordering a
composite index wants.

## The test

```java
class SchemaMigrationTest extends OracleTestBase {

    @Test
    void slotsAndBookingsTablesExist() {
        Integer tables = jdbc.queryForObject(
                "SELECT COUNT(*) FROM user_tables WHERE table_name IN ('SLOTS','BOOKINGS')",
                Integer.class);
        assertThat(tables).isEqualTo(2);
    }

    @Test
    void databaseRefusesToOversellASlot() {
        jdbc.update("INSERT INTO slots (service_date, service_time, capacity, seats_taken) "
                + "VALUES (DATE '2026-10-01', '19:00', 250, 0)");

        assertThatThrownBy(() ->
                jdbc.update("UPDATE slots SET seats_taken = 251 "
                        + "WHERE service_date = DATE '2026-10-01' AND service_time = '19:00'"))
                .hasMessageContaining("CK_SLOTS_SEATS");
    }
}
```

`user_tables` is an Oracle data dictionary view listing tables owned by the
current user. Table names are stored uppercase unless quoted at creation.

**The second test is the one that matters.** It contains no application code at
all — it issues raw SQL and asserts the *database* refuses it. Oracle answers:

```
ORA-02290: check constraint (BOOKING.CK_SLOTS_SEATS) violated
```

`BOOKING` is the schema owner; `CK_SLOTS_SEATS` the constraint, uppercased.

Asserting on the constraint *name* rather than just "some exception was thrown"
is deliberate: it proves the rejection came from the intended constraint and
not incidentally from something else — a `NOT NULL`, a type overflow, a
different check.

### Why the test is re-runnable

It inserts a hardcoded `(2026-10-01, '19:00')`, is not `@Transactional`, and so
commits for real. With Testcontainers reuse enabled, that row would still be
there on the next run and collide with `uq_slots_datetime`.

It does not, because `OracleTestBase.@BeforeEach` clears both tables before
every test method. That cleanup exists precisely for this
([note 01](01-project-skeleton-and-spring-boot-basics.md) explains the two
failures it prevents).

## TDD in practice here

The sequence was:

1. **RED** — write the test, run it, watch it fail with
   `ORA-00942: table or view "BOOKING"."SLOTS" does not exist`. This is the
   *expected* failure: the table genuinely does not exist yet.
2. **GREEN** — write the migration, re-run, watch Flyway apply it and the
   tests pass.

The discipline point is step 1. A test that has never been observed failing has
not been shown to test anything — it might pass because the assertion is
vacuous, or because it is not running at all. Watching it fail *for the reason
you predicted* is what makes the subsequent pass meaningful.

That principle earned its keep in this task. When the tests failed with
`ORA-00942` even after the migration existed, the RED-phase experience was what
made it obvious the failure mode was unchanged — the migration was not running
at all, rather than running and being wrong.
